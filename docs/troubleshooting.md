## 1. RSS 수집 · 파싱

### 1.1. RSS 한글 문자 출력 꺠짐, 인코딩 처리

#### 문제

한겨레 RSS를 추가했을 때 기사는 화면에 출력되었지만 제목과 작성자 등의 한글이 깨졌다. RSS 요청부터 XML 파싱, 기사 추출까지는 진행되고 있었으므로 태그 구조보다 문자열이 만들어지는 과정을 먼저 확인했다.

브라우저에서는 같은 RSS의 한글이 정상적으로 보였다. 실제 GET 응답의 `Content-Type`은 `application/xml`이었지만 charset은 없었고, XML에도 인코딩 선언이 없었다. 응답 본문을 파일로 저장해 확인했을 때는 UTF-8로 판별되었다. 파일 형식 판별 결과만으로 인코딩을 확정할 수는 없지만, 브라우저 표시와 응답 정보를 함께 보았을 때 원본 바이트보다 애플리케이션의 디코딩 과정에 문제가 있다고 판단했다.

기존에는 `body(String.class)`로 응답을 문자열로 받은 후 `StringReader`를 통해 DOM 파서에 전달했다. 이 흐름에서는 DOM 파서가 XML을 읽기 전에 이미 문자열이 만들어진다. 바이트를 잘못된 문자셋으로 변환했다면 이후 XML 파싱 과정에서 원래 문자를 복구할 수 없었다.

#### 해결

`fetchRss()`에서 응답 헤더와 바이트를 직접 다룰 수 있도록 `exchange()`를 사용했다. HTTP 응답에 charset이 있으면 해당 값을 사용하고, 없으면 UTF-8을 기본값으로 사용했다.

```java
MediaType contentType = response.getHeaders().getContentType();
Charset charset = contentType == null ? null : contentType.getCharset();

if (charset == null) {
  charset = StandardCharsets.UTF_8;
}

byte[] body = response.getBody().readAllBytes();
return new String(body, charset);
```

한겨레 구현체 안에만 예외 처리를 넣는 대신, 공통 요청 과정에서 응답의 charset을 우선하도록 했다. XML 선언 분석이나 인코딩 자동 판별까지 확장하는 방법도 생각했지만, 당시 확인한 문제를 해결하는 범위로 구현했다.

#### 정리

현재 처리는 모든 인코딩을 자동으로 알아내는 방식은 아니다. charset이 없는 응답에 UTF-8을 적용하는 정책이며, 다른 인코딩을 사용하는 소스가 추가된다면 다시 검토해야 한다.

### 1.2. 매체별 필수·선택 XML 필드 처리

#### 문제

RSS를 추가하면서 모든 기사에 이미지 태그가 있는 것은 아니라는 점을 확인했다. 기존처럼 태그가 있다고 가정하고 메서드를 연달아 호출하면, 선택 정보가 없는 기사에서도 예외가 발생했다.

제목과 링크는 기사 표시와 원문 이동에 필요했지만 설명, 발행일, 작성자, 이미지는 매체나 기사에 따라 생략될 수 있었다. 제목, 링크 같은 필수적인 정보와 선택적인 필드를 구분해 소스를 선별하기로 했다.

#### 해결

제목과 링크가 없으면 해당 기사를 건너뛰고, 선택 필드는 없을 때 `null`로 두도록 처리했다. 이 과정에서 `getElementsByTagName()`과 `item(0)`의 반환값도 구분해야 했다. 태그가 없으면 빈 `NodeList`가 반환되고, 그 목록의 첫 항목을 요청하면 `null`이 반환된다.

```java
Node titleNode = itemElement.getElementsByTagName("title").item(0);
if (titleNode == null) {
  continue;
}
String title = titleNode.getTextContent();
```

선택 필드는 노드의 존재 여부를 확인한 뒤 값만 결정했다. 이미지가 없는 경우에는 HTML에서도 thymeleaf의 `th:if` 문법을 사용해 이미지 태그자체를 출력하지 않도록 했다.

#### 정리

소스 요청 자체가 실패한 경우, 기사에 필수 정보가 없는 경우, 선택 정보만 없는 경우를 서로 다른 범위로 처리했다. 단, 현재 필수 필드 검사는 태그의 부재를 다루는 수준이며 빈 문자열이나 공백만 있는 값까지 모두 검증하는 것은 아니다.

### 1.3. 특정 소스의 수집 실패 시 나머지 소스 처리 지속

#### 문제

여러 RSS를 순서대로 수집하면서 한 매체의 요청 실패가 전체 작업을 종료시키지 않도록 해야 했다. 매체별 수집은 서로 독립적으로 사용할 수 있으므로, 실패한 소스만 건너뛰는 방향으로 구성했다.


#### 해결

예외 처리를 전체 반복문 바깥에 두는 대신 소스 하나를 처리하는 반복문 안에 두었다. 루프 안에서 `fetch → parse → extract` 중 예외가 발생하면 해당 RSS URL과 예외메시지를 출력하고 다음 반복으로 이동한다.

### 1.4. 수집 실패 시 기존 스냅샷 관계 보존

#### 문제

갱신을 위해 먼저 기존 목록을 삭제한 뒤 RSS를 요청하면, 요청이 실패했을 때 정상적으로 저장된 목록까지 잃을 수 있다.

#### 해결
RSS 요청과 파싱, 기사 추출을 마친 후 관계를 비교하도록 했다. 앞 단계에서 예외가 발생하면 해당 소스의 관계 갱신으로 넘어가지 않아 기존 관계가 남는다.

#### 검증

NYT RSS를 정상적으로 수집한 뒤 URL을 의도적으로 변경해 요청을 실패시켰다. `ResourceAccessException` 발생 후에도 기존 NYT World 관계가 유지되는 것을 확인했다.

여기서 보존하는 것은 오늘 스냅샷에 이미 저장되어 있던 해당 소스의 상태다. 오늘 첫 수집부터 실패한 경우에 전날 목록을 자동으로 복사하는 처리는 구현하지 않았다.

현재 추출 결과가 예외 없이 빈 리스트로 반환되면, 오늘 스냅샷에 있던 해당 소스의 관계는 제거된다. 실패를 빈 목록으로 바꾸지 않는 것이 중요한 이유다.

## 2. DB·JPA

### 2.1. Repository 메서드명과 엔티티 필드명 불일치

#### 문제

기사에 연결 관계가 남아 있는지 확인하려고 `existsByArticleEntity(...)`를 작성했을 때 조회 경로를 찾지 못하는 오류가 발생했다.

```text
UnknownPathException
Could not resolve attribute 'articleEntity'
```

#### 원인과 해결

Spring Database JPA가 제공하는 API 중 필드명으로 findBy, existsBy 메서드를 선언만으로 사용할 수 있는 기능을 쓰면서 제대로 된 필드명을 인가하지 못해 발생한 문제로 파악됐다.
관계 엔티티의 실제 필드는 `private ArticleEntity article;`이었다.

메서드 이름을 `existsByArticle(...)`로 변경해 실제 엔티티 속성과 일치시켰다. 이 메서드를 통해 오래된 관계를 삭제한 후에도 해당 기사를 참조하는 관계가 있는지 확인하도록 했다.

### 2.2. 기사 설명의 varchar(255) 길이 제한 초과

#### 문제
RSS를 DB에 저장하면서 다음 오류가 발생했다.

```text
value too long for type character varying(255)
```

어떤 값이 제한을 넘었는지 확인하기 위해 필드별 길이를 비교하니 description 필드가 약 300자 이상의 문자열로 나타났다. Java에서는 `String`으로 다룰 수 있는 값이지만 DB의 `description` 컬럼은 255자로 제한되어 있다는 것을 확인했따.

#### 해결

기사 요약은 매체마다 길이가 달라질 수 있으므로 `description`을 `TEXT`로 저장하도록 변경했다.

```java
@Column(columnDefinition = "TEXT")
private String description;
```
`description`에 `@Column(columnDefinition = "TEXT")`를 추가했지만 기존 DB의 컬럼은 계속 `varchar(255)`로 남아 있었다. 엔티티 선언을 변경하면 이미 만들어진 스키마도 원하는 형태로 바뀔 것이라고 생각한 부분에서 문제가 생겼다.

엔티티 코드와 실제 DB 컬럼을 따로 확인했다. 당시 사용하던 `ddl-auto` 설정에만 맡기지 않고, 기존 컬럼을 직접 변경했다.

```sql
ALTER TABLE article_entity
ALTER COLUMN description TYPE TEXT;
```

#### 정리

입력값의 Java 타입만 보고 저장 가능 여부를 판단할 수 없었다. 오류를 낸 컬럼과 실제 데이터 길이를 확인한 뒤, 데이터의 용도에 맞춰 저장 타입을 결정했다.

### 2.3. 같은 기사·스냅샷 관계의 중복 방지

#### 구현 과정

하루에 여러 번 수집하므로 같은 기사가 다시 들어올 수 있다. 이때 기사 자체를 새로 만들지 않는 것과 오늘 스냅샷에 같은 연결을 또 만들지 않는 것은 다른 문제였다.

뉴스를 제공하는 매체에서 같은 링크를 통해 다른 기사를 제공하는 일은 없을 것이라고 가정해 기사 링크로 `ArticleEntity`를 조회해 존재하면 재사용하도록 했다. 이후 오늘 스냅샷에 연결된 관계를 확인하고, 같은 링크의 기사와 이미 연결되어 있으면 `ArticleSnapshotEntity`를 추가하지 않는다.

### 2.4. RSS 목록 변경에 따른 스냅샷 관계 추가·제거

#### 문제와 로직 구성

스냅샷을 그날의 마지막 수집 목록으로 유지하려면 새 기사를 추가하는 것만으로는 부족했다. 현재 RSS에서 사라진 기사와의 연결도 제거해야 했다.

DB의 기존 관계를 기준으로 현재 RSS 전체에서 같은 링크를 찾고, 끝까지 찾지 못한 경우에만 삭제하도록 했다. 첫 번째 비교에서 링크가 다르다고 바로 삭제하면 뒤에 같은 기사가 있어도 관계를 잘못 제거할 수 있었다.

반대로 현재 RSS에 있는 기사를 기준으로 오늘 스냅샷의 관계를 확인하고, 없는 연결만 추가했다. 두 비교 모두 현재 처리 중인 소스의 상태를 반영하도록 구성했다.

#### 삭제 후 재조회

DB에서 관계를 삭제해도 앞서 조회한 Java 리스트의 원소가 자동으로 제거되는 것은 아니었다. 삭제된 관계를 포함한 옛 리스트로 다음 판단을 하지 않도록, 제거 단계가 끝난 뒤 관계를 다시 조회했다.

## 3. 화면 출력

### 3.1. Flex 레이아웃에서 sticky 위치 고정 문제

#### 문제

뉴스 목록을 내리는 동안 날짜 선택 네비게이터의 위치를 스크롤 내에 유지하기위해 `position: sticky`를 적용했지만 기대한 대로 동작하지 않았다.

부모 컨테이너가 Flex 레이아웃이었고, 뉴스 기사 영역과 네비게이터이 같은 레벨로 배치된 것이 원인이었다. 표시된 컨텐츠 영역은 작았으나, stretch 동작으로 날짜 네비게이터의 영역이 긴 뉴스 영역의 높이까지 늘어나 있었다. 영역이 너무 커 커테이너 내에서 이동하지 못하는 것이 원인이었다.

#### 해결

날짜 영역에 `align-self: flex-start`를 적용해 콘텐츠 높이를 유지하도록 했다.

```css
.remote {
  position: sticky;
  top: 100px;
  align-self: flex-start;
}
```

#### 정리

sticky 속성만 확인해서는 원인을 찾기 어려웠다. 부모의 레이아웃 방식과 자식 요소가 실제 차지하는 높이를 함께 확인해야 했다.

## 4. 배포

### 4.1. SSH 접속 실패와 네트워크·인증 문제 구분

#### 문제

EC2 Ubuntu 서버에 처음 접속할 때 `Connection reset by peer` 또는 `Operation timed out`이 발생했다. 특히 도서관 Wi-Fi와 휴대전화 핫스팟에서 보안 그룹의 SSH 허용 대상을 `My IP /32`로 설정했을 때 연결이 되지 않았다.

#### 해결

인증 단계까지 도달하지 못하는 연결 문제로 보고, 진단을 위해 SSH 허용 대상을 일시적으로 넓혔을 때 접속에 성공했다. 이를 통해 당시에는 키 파일 자체보다 허용한 Source IP와 실제 연결의 출발 IP 사이의 문제로 판단했다.

[목차로 이동](#목차)

### 4.2. Nginx 기본 사이트와 애플리케이션 프록시 설정 충돌

#### 문제

Nginx를 80번 포트의 진입점으로 설정했지만, 외부에서 News Reader 대신 기본 환영 페이지나 Nginx의 404 페이지가 표시되었다.

서버 내부에서 `curl http://localhost`로 응답을 확인했을 때도 기본 페이지가 나왔다. 이 요청에 대한 문제가 외부 보안 그룹보다 Nginx 내부의 사이트 선택에 있다고 범위를 좁혔다.

설치 시 기본으로 활성화된 `/etc/nginx/sites-enabled/default`가 남아 있어, 애플리케이션으로 전달할 설정 대신 기본 사이트가 요청을 처리하고 있었다.

#### 해결

기본 사이트의 활성화 링크를 제거하고 `nginx -t`로 설정을 검사한 뒤 Nginx를 reload했다. 이후 서버 내부 요청에서 News Reader HTML을 받고 외부 브라우저에서도 정상 접근을 확인했다.
